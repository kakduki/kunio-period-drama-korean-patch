# 실시간 번역 병행 전략

## 결론

실시간 AI 번역 오버레이는 네이티브 한글 패치의 대체품이 아니라, 자연 플레이와 대사 수집을 즉시 시작하기 위한 병행 경로로 채택한다.

현재 저장소의 `scripts/run_realtime_overlay.py`는 FCEUX Lua 이벤트를 받아 검증된 번역 캐시를 화면에 표시한다. 따라서 자동으로 게임을 클리어하려고 하지 않고, 사용자가 직접 플레이하는 동안 오버레이를 유지할 수 있다. 다만 아직 임의의 일본어 화면을 OCR로 읽어 AI에 보내는 완전 자동형은 아니다.

## 왜 영어 레퍼런스가 있어도 네이티브 패치가 오래 걸리는가

영어 IPS는 문자열의 최종 의미와 일부 위치 이동을 알려 주는 강한 구조 레퍼런스다. 하지만 그것만으로 다음 문제가 자동 해결되지는 않는다.

- 일본어 원본의 포인터 테이블과 영어판의 확장 문자열 위치를 일대일로 확정해야 한다.
- 일본어 바이트가 실제 화면의 글리프와 어떤 관계인지 확인해야 한다. 일반 Shift-JIS 텍스트 파일처럼 바로 치환할 수 없다.
- 한글은 일본어 원본 폰트보다 글리프 수와 폭이 커서 폰트, 타일, 줄바꿈, 문자열 길이까지 함께 바뀔 수 있다.
- 정적 바이트 후보는 아이템명이나 코드 데이터와 겹칠 수 있다. 실제 CPU 읽기, PPU 화면, context가 확인되기 전에는 패치하면 오작동할 수 있다.
- 보스 대사는 전투 이벤트가 자연스럽게 발생해야 화면 증거를 얻을 수 있다. 영어 패치는 게임플레이를 자동 진행시키는 치트나 보스 워프가 아니다.

현재 상태는 영어 레퍼런스 기반의 248개 포인터 카탈로그와 144개 번역 후보를 확보했지만, 네이티브 화면 증거가 확인된 문자열만 안전하게 후보 ROM에 넣는 단계다.

## 두 트랙 운영

### 트랙 A: 즉시 플레이용 오버레이

```powershell
python scripts/run_realtime_overlay.py --rom "rom\\Kunio Kun no Jidaigeki Dayo Zenin Shuugou! (J).nes"
```

- FCEUX는 수동 조작으로 계속 진행한다.
- 검증된 이벤트는 한국어 캐시를 즉시 표시한다.
- 미확인 이벤트를 외부 번역 명령에 연결할 수 있지만 결과는 `AI_UNCHECKED`로 기록한다.
- AI 결과는 자동으로 ROM에 삽입하지 않는다.
- 이벤트와 초안은 `rom_analysis/realtime_overlay/`에 남겨 나중에 네이티브 패치 후보로 승격한다.

이 경로는 보스까지 직접 플레이하면서 대사를 확인할 때 가장 빠른 현재 수단이다. 기존 자동 주행처럼 첫 화면에서 무한 반복하지 않는다.

### 트랙 B: 배포용 네이티브 패치

1. 오버레이 이벤트에서 실제 대사와 context를 수집한다.
2. 영어 레퍼런스와 일본어 원문을 대조해 번역을 확정한다.
3. 실제 화면 표시가 확인된 문자열만 폰트/포인터/문자열 데이터를 패치한다.
4. 후보 ROM을 재빌드하고 FCEUX 부팅 및 해당 화면을 검증한다.
5. 최종 릴리스에서는 모든 대사와 보스/엔딩 경로를 재검증한다.

## AI 오버레이의 한계와 다음 확장

현재 이벤트 방식은 이미 확인된 메모리 문자열에 강하다. 임의 화면까지 다루려면 다음 순서가 필요하다.

1. FCEUX PPU/nametable 또는 화면 캡처를 확보한다.
2. 일본어 타일을 문자로 복원하는 게임 전용 디코더를 붙인다.
3. 디코더가 실패할 때만 OCR/AI를 호출한다.
4. 같은 화면의 반복 호출은 캐시하고, 번역 결과와 원문 이미지/바이트를 함께 저장한다.
5. 검토 전 결과는 항상 `AI_UNCHECKED`로 유지한다.

즉, AI는 수집과 임시 플레이에는 매우 유용하지만, 폰트와 포인터가 맞아야 하는 최종 ROM 패치를 대신하지는 않는다.
